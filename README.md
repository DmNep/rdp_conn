# rdp_conn

[![license: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Канал управления между двумя Windows-машинами через **буфер обмена RDP**.

Нужен ровно тогда, когда между машинами остался только RDP. Проверялось на
стенде, где на одной стороне захват звука отдаёт 0 устройств из 19, на другой
политика запрещает запись, а из сети наружу разрешён только порт 3389 — то есть
сам RDP. Буфер обмена живёт внутри того же соединения, поэтому каналу не нужны
ни открытые порты, ни звук, ни права администратора.

```
машина A (клиент mstsc)  ── RDP, редирект буфера ──  машина B (сессия)
       rdpconn.tx          ──── кадры с CRC ────       rdpconn.rx --exec
```

Команда уходит кадром `CMD`, обратно приходит подтверждение `ACK` и вывод
команды `NOTE`. Никаких сокетов: один текстовый слот, в котором живут последние
кадры обеих сторон.

## Установка

Нужен только Python 3.10+. Внешних зависимостей нет намеренно: канал нужен
ровно тогда, когда на второй машине нельзя ничего поставить и поднять.

```text
git clone https://github.com/DmNep/rdp_conn.git
cd rdp_conn
set PYTHONPATH=%CD%
```

Ставить пакет не обязательно — `python -m rdpconn` работает из каталога.

## Быстрый старт

Сторона B — приёмник, внутри RDP-сессии:

```text
python -m rdpconn rx --peer-id B --exec
```

Сторона A — отправитель, на машине с запущенным mstsc:

```text
python -m rdpconn tx --peer-id A --repl
```

Метка `--peer-id` обязательна на обеих сторонах и не по вкусу: без неё метка
случайная, и каждый перезапуск стороны выступает под новым id, а собеседник
теряет возможность сопоставить кадры одного конца до и после перезапуска.

На B держите ровно **один** `rx`. Два приёмника с одним `--peer-id` дают лавину
подтверждений на каждый кадр: обмен визуально работает, но тонет в повторе.

## Что происходит на одном шаге

| Шаг | Кадр | Смысл |
|---|---|---|
| 1 | `CMD seq=0` | текст команды |
| 2 | `ACK seq=0` | кадр дошёл (не «команда выполнена») |
| 3 | `NOTE seq=0` | вывод команды, пакетами по 240 байт |

Без `--exec` на третьем шаге уходит эхо принятого текста байт-в-байт — дешёвая
проверка, что кодовая страница сторон не разъехалась.

## Ключевые флаги

| Флаг | Сторона | Зачем |
|---|---|---|
| `--peer-id A\|B` | обе | метка конца в слоте, обязательна в бою |
| `--exec` | rx | исполнять команду и возвращать вывод |
| `--repl` | tx | читать команды с клавиатуры |
| `--hotkey ctrl+alt+f9` | обе | отдать буфер человеку, повторное нажатие продолжит обмен |
| `--ping 25` | tx | интервал контрольных кадров; меньше 10 не ставить |
| `--slot file:PATH` | обе | слот в файле: проверить весь обмен одной машиной |
| `--codepage cp866` | обе | кодовая страница текста |

`--ping` ниже 10 ломает канал на живом редиректе: буфер в RDP сам по себе
запаздывает на единицы-десятки секунд, и живой собеседник объявляется
потерянным. Порог молчания — `--ping` × 3.

Хотите копировать своё и не мешать обмену — не ставьте `--hotkey`: приёмник
заметит человеческую копию, скажет о ней, но подтверждение всё равно отправит.
Буфер отдать целиком можно только клавишей.

## Шлюз в интернет и локальная модель

Поверх того же буфера и того же кадра `NOTE` (раскладка не меняется, своя
магия внутри payload) живут ещё четыре режима — одновременно с `tx`/`rx` их
не запускают, слот один:

```text
python -m rdpconn gate listen --peer-id B    прокси там, где нет интернета
python -m rdpconn gate dial --peer-id A      выход в интернет на этой машине
python -m rdpconn coder host --peer-id A     текст локальной модели на этой машине
python -m rdpconn coder guest --peer-id B    тот же текст для Cline в сессии
python -m rdpconn host --feed model          то же, что coder host, плюс страница статистики
python -m rdpconn guest --feed model         то же, что coder guest, одна роль на запуск
python -m rdpconn host --feed net            то же, что gate dial
python -m rdpconn guest --feed net           то же, что gate listen, прокси только на 127.0.0.1
python -m rdpconn monitor                    смотреть слот с этой машины, не записывая его
```

`gate` — HTTP-прокси через буфер: `listen` на машине без сети поднимает
локальный прокси (по умолчанию `127.0.0.1:8079`), программа (Кода, VS Code)
указывает его в `requestOptions.proxy`; `dial` на машине с интернетом
открывает обычный TCP и возвращает ответ. Описано в
[docs/protocol.md](docs/protocol.md), разделы 10 и 13.

`coder` — текст локальной модели через тот же буфер, без HTTP и без порта:
`host` рядом с моделью говорит с OpenAI-совместимым сервером, `guest` в
сессии отдаёт тот же текст построчным JSON на stdin/stdout — на этом держится
провайдер Cline, [cline/rdpconnHandler.ts](cline/rdpconnHandler.ts).

`host`/`guest --feed model|net` — тот же `coder`/`gate` одним входом, плюс у
`host` веб-страница статуса (по умолчанию `127.0.0.1:8078`, `--monitor ""`
выключает). Отдельная команда `monitor` поднимает такую же страницу, ничего
не пишет в слот и не мешает `coder`/`gate` на второй машине.

`coder`, `host`/`guest` и `monitor` не описаны в `docs/protocol.md` — спека
сейчас покрывает только `tx`/`rx`/`gate`.

| Флаг | Где | Назначение |
|---|---|---|
| `--feed model\|net` | `host`/`guest` | режим: текст модели или интернет (обязателен) |
| `--upstream URL` | `host`, модель | OpenAI-совместимый адрес модели на этой машине (по умолчанию `http://127.0.0.1:8080/v1`) |
| `--model NAME` | `host`, модель | имя модели в запросе; пусто — как решит сервер |
| `--once FILE` | `guest`, модель | один запрос из JSON-файла и выход, без REPL |
| `--cells N` | модель | ячеек данных в снимке кодера |
| `--proxy HOST:PORT` | `gate`/`guest --feed net` | локальный прокси, только `127.0.0.1` (по умолчанию `127.0.0.1:8079`) |
| `--monitor HOST:PORT` | `gate`/`host` | страница статистики, только `127.0.0.1`; пусто — не поднимать |

## Проверка без второй машины

`--slot file:PATH` заменяет буфер обмена файлом, и оба конца запускаются на одной
машине. Хранилище отслоено, поэтому маркер, история слота, занятость и пауза
проверяются без Windows API.

```text
python tools/test_frames.py      # кадр, CRC, разбор, точка входа
python tools/test_clipboard.py   # слот: маркер, история, пауза, занятость
python tools/test_heartbeat.py   # PING/PONG, молчание, возврат после обрыва
python tools/test_duplex.py      # tx и rx двумя процессами через один слот
python tools/test_gate.py        # прокси через буфер: listen/dial
python tools/test_coder.py       # текст модели через буфер: host/guest
python tools/test_statcell.py    # служебная ячейка статистики гуеста
python tools/test_monitor.py     # чтение слота без записи
python tools/test_tune.py        # замер паузы повтора и рабочий запас
python tools/test_ceiling.py     # потолок снимка без буфера
python tools/test_sim_clipboard.py  # искусственная задержка, --slot sim:DELAY[,JITTER][:PATH]
python tools/test_tx_wait.py     # ACK ждём по heartbeat, не по отдельному таймеру
python tools/test_reconnect.py   # после обрыва PING не глохнут, а идут реже
python tools/test_gate_sim.py    # gate под инъецированной задержкой, бэкофф повтора
python tools/bench_speed.py --win     # скорость: кадр/с, байт/с, задержка шага
python tools/bench_speed.py --rtt-only  # задержка шага, без дочерних процессов
python tools/bench_speed.py --remote    # бой: rx на второй машине, виден редирект
python tools/bench_speed.py --bulk      # латентность или пропускная способность
```

Первые четырнадцать — скрипты без зависимостей, заканчиваются строкой с `ALL GREEN`
(у части — `RESULT: ALL GREEN`, у части просто `ALL GREEN`, точный префикс не
единый).

### Замер в бою

`--remote` — единственный режим, который видит редирект RDP: он поднимает
только `tx`, а `rx` должен работать на второй машине. Локальные слои на стенде
дают оптимистичную цифру локального буфера, и отличить её от настоящей по
выводу нельзя.

```text
B: python -m rdpconn.rx --peer-id B --ping 0 --no-echo --wait 25 --duration 900
A: python tools/bench_speed.py --remote --proc-frames 20 --remote-wait 25
```

Скрипт сам печатает готовую команду для B, очищает слот перед прогоном и
считает шаг от `>> CMD` до `<< ACK` построчно — поэтому старт интерпретатора и
ожидание подтверждения в цифру не попадают. `--remote-wait` меньше 20 с ставить
бессмысленно: подтверждение придёт после объявления тишины, и замер измерит
ретрансляции, а не канал.

Строка `!! прогон нечист` означает, что цифру брать нельзя: в ней число
ретрансляций, тишин и старых кадров. Последние — признак того, что слот был
забит наследием прежнего обмена; сам канал лишние `rx` не вычисляет, «ровно один
приёмник» остаётся требованием к прогону (AGENTS.md 3).

`--remote-reply-wait` по умолчанию 0 без `--echo`: `rx` с `--no-echo` молчит, а
ожидание стоило бы дороже самого шага. С `--echo` по умолчанию 3. Эхо не входит
в шаг `CMD`→`ACK` (приёмник подтверждает до эха) — оно входит в «время на
команду», то есть в реальную пропускную способность: при эхе шаг остаётся
прежним, а команда стоит ещё один цикл редиректа плюс ожидание NOTE.

### Поможет ли батчинг: `--bulk`

Прежде чем менять протокол ради скорости, надо узнать, чем она ограничена:
латентностью события редиректа или его пропускной способностью. Штатный обмен
этого не покажет — кадр всегда один и тот же, 240 байта. `--bulk` гоняет
нагрузку разного размера и смотрит, растёт ли RTT вместе с ней. Крупнее
16 КБ она уходит несколькими записями этого размера: следующая начинается
после ответа на текущую.

```text
B: python tools/bench_speed.py --bulk-listen --bulk-wait 600   # штатный rx остановить
A: python tools/bench_speed.py --bulk --bulk-wait 60
```

Если RTT почти не меняется при росте записи в разы — это латентность, и весь
дефицит закрывается батчингом (больше байт на шаг, один `ACK` на пачку, zlib).
Если RTT растёт вместе с размером — это пропускная способность, батчинг её не
обманет и транспорт под агента надо менять.

Запись намеренно не собирается в кадр (иначе `MAX_PAYLOAD = 240` не дал бы
измерить ничего больше 240 байт), а её содержимое — псевдослучайные байты:
повторяющийся заполнитель сжался бы редиректом, и мёрился бы сжатие, а не
канал. Ответ помечен первыми байтами запроса, иначе опоздавший ответ прошлого
прогона засчитался бы как текущий (на файле это давало 2.1 МБ/с из ниоткуда).

## Ограничения

- **Шифрования и аутентификации нет.** Буфер читает любое приложение сессии;
  метка стороны защищает от рассинхронизации, а не от чужого процесса. Для
  чувствительных команд канал не предназначен.
- **Кадру нужно быть текстом**, поэтому он в base64: 240 байт кадра дают ~330
  символов в буфере.
- **Файлы и терминал не передаются.** `--exec` — запуск одной команды с
  возвратом вывода; для файлов есть сам RDP.
- **Один отправитель на слот.** Ячейки подписаны, но очередь на подтверждение
  одна.

машине не нужен: зависимостей нет, достаточно распаковать и задать `PYTHONPATH`.
