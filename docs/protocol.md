# Спецификация канала rdp_conn

Настоящий документ — источник истины по формату обмена. Реализация —
`rdpconn/`; единственное место, где значения протокола заданы числом, —
`rdpconn/config.py`. Расхождение кода со спецификацией считается ошибкой кода.

Номера разделов используются в комментариях исходников (`docs/protocol.md 4`),
поэтому их стоит сохранять.

## 1. Назначение и границы

Канал нужен, чтобы управлять второй Windows-машиной, когда между машинами
работает только RDP. Проверялось на стенде, где на одной стороне захват звука
отдаёт 0 устройств из 19, на другой политика запрещает запись, а из сети наружу
разрешён только порт 3389 — то есть сам RDP. Буфер обмена живёт внутри этого же
соединения, поэтому каналу не нужны ни открытые порты, ни звук, ни права
администратора.

Состав: `rdpconn.tx` — отправитель (сторона клиента RDP), `rdpconn.rx` —
приёмник (сторона сессии). Оба — консольные, только stdlib + Windows API через
ctypes.

Границы. Канал передаёт кадры и исполняет по одному текстовому действию на
стороне приёмника. Он не передаёт файлы, не работает как терминал и не
рассчитан на несколько отправителей в один слот.

## 2. Буфер обмена как транспорт

Слот — текстовый буфер обмена (`CF_UNICODETEXT`). Выбран только текст: он
переживает RDP-редирект и совместим с любым приложением, а произвольный формат
через сессию не проходит. Отсюда base64 в тексте слота.

Текст слота — набор подписанных ячеек:

```
RDP1|<id>:<номер>:<base64>|<id>:<номер>:<base64>|...
```

- `RDP1` — префикс и версия формата. Версия зашита в префикс, а не в поле
  внутри ячейки: расхождение версий обязано дать пустой разбор, а не неверно
  прочитанный кадр. Смешивать концы разных версий нельзя — обмен не состоится,
  но и не испортит данные.
- `<id>` — метка стороны (`--peer-id`, на практике `A` и `B`). Не содержит `:`
  и `|`, иначе разбор ячейки неоднозначен.
- `<номер>` — счётчик исходящих ячеек стороны, растёт на каждую запись.
- ячеек на сторону до `HISTORY_SLOTS` (сейчас 20): шаг обмена — это
  несколько ячеек, и короткая история стирает предыдущую, не дав
  собеседнику её прочитать. Ответ `--exec` — это ACK и до 18 NOTE (вывод
  режется по 240 байт, потолок 4096). Вся эта пачка пишется в буфер одной
  записью: отдельные записи оставляют редиректу промежуточный снимок, и
  хвост вывода уже не доезжает. В этой записи только ячейки текущего
  ответа, без NOTE прошлых команд. Отдельный кадр (CMD, PING) по-прежнему
  сохраняет несколько своих последних ячеек.

Приём считает кадр новым по паре (номер, содержимое). Решать по одному номеру
нельзя: после перезапуска собеседника его счётчик снова идёт с единицы, и приём
оглох бы навсегда. Решать по одному содержимому нельзя: вторая одинаковая
команда подряд была бы потеряна.

Два состояния слота различаются намеренно:

- **занят** (`busy`) — в слоте человеческая копия. Запрещает только запись;
  приём продолжается. Запрет приёма означал бы тупик: буфер в RDP-сессии почти
  всегда занят посторонним, приёмник не смог бы подтвердить кадр, отправитель
  ретранслировал бы его вечно. Снимается само по таймауту
  (`--pause-timeout`).
- **пауза** (`paused`, `--hotkey`) — буфер целиком отдан человеку, запись
  запрещена, приём продолжается. `--restore` возвращает последний наш кадр,
  но только если в слоте по-прежнему нет человеческой копии.

## 3. Кадр

```
 0        1        2       3    4        5..5+len-1   +2
+--------+--------+-------+----+--------+------------+------+
|  sync  |  type  |  seq  |    len     |   payload  | crc  |
+--------+--------+-------+----+--------+------------+------+
   0x7E     байт    байт      2 байта      len байт   2 байта
```

- `len` — длина payload, big-endian, максимум `MAX_PAYLOAD = 240`.
- `crc` — CRC-16/CCITT-FALSE от всех предшествующих байтов кадра (включая
  заголовок), big-endian. Параметры: полином `0x1021`, инициализация `0xFFFF`,
  без реверса входных и выходных бит, `xorout = 0x0000`. Контрольная сумма
  строки `123456789` равна `0x29B1`; этим значением проверяется реализация,
  потому что близкие варианты (XMODEM с init `0x0000`, REVERSE с реверсом бит)
  на глаз неотличимы и дают молчаливый рассинхрон сторон.

Порядок байтов и длина обязательны на обеих сторонах: буфер передаёт кадр
целиком в тексте слота, поэтому здесь не нужны ни обрамление по паузам, ни
предыстория, ни выравнивание по символам — достаточно границы кадра, длины и
контрольной суммы.

`0x7E` выбран как сохранение совместимости с аудио-предшественником: в тексте
слота байт прячется за base64, а готовый разбор кадра остаётся общим.

## 4. Типы кадров и цикл обмена

| Тип   | Код  | Направление | payload             | Ждёт ACK |
|-------|------|-------------|---------------------|----------|
| `CMD` | 0x10 | tx → rx     | текст команды       | да       |
| `NOTE`| 0x22 | любая       | текст ответа / эхо  | нет      |
| `ACK` | 0x03 | любая       | пусто               | нет      |
| `NAK` | 0x04 | любая       | 1 байт причины      | нет      |
| `PING`| 0x41 | tx → rx     | пусто               | нет      |
| `PONG`| 0x42 | rx → tx     | пусто               | нет      |

Обмен полудуплексный, шаг один: отправитель шлёт `CMD` и ждёт `ACK` с тем же
`seq`; приёмник разбирает кадр и отвечает `ACK`.

Несколько коротких команд, которые уже лежат в очереди, уходят одним снимком.
Сколько их класть, решает длина очереди: одна команда — один кадр, сколько
ожидает и влезает — столько кадров. Потолок — `HISTORY_SLOTS` ячеек и 16 КБ
полезной нагрузки. Ответ на короткую команду — `ACK` и `NOTE`, поэтому таких
команд в снимке не больше половины ячеек: иначе подтверждения не влезут в
ответный снимок. Приёмник отвечает на все команды этого снимка одной записью,
по `ACK` на каждый `seq`. Какой `seq` в ответе не назван, тот повторяется с
тем же номером. Команда длиннее кадра по-прежнему едет отдельно, своими
кусками. Вывод `--exec` дописывается в тот же ответный снимок, пока хватает
ячеек. Длинный вывод занимает их сам, и следующая команда этого приёма в
снимок уже не берётся: подтверждения важнее хвоста.

- **Подтверждение означает «кадр дошёл», а не «команда выполнена»**. Исполнение
  на приёмнике по умолчанию выключено: именно молчаливое «принял и молчу» делало
  канал односторонним.
- **`seq` — счётчик исходящих кадров стороны**, 0..255 по кругу, независимый у
  каждой стороны.
- **Повтор обязан идти с тем же `seq`.** Повтор с новым номером неотличим от
  новой команды, и приёмник исполнил бы её второй раз. Сторона, уже
  использовавшая команду, на повтор с тем же номером отвечает закешированным
  ответом, а не исполняет повторно.
- `ACK` идёт пустым: номер уже стоит в заголовке, дублировать его вторым байтом
  — значит дать два источника правды про один `seq`. У аудио-предшественника
  payload `ACK` был `(seq,)`, а `NAK` — `(seq, reason)`; здесь `NAK` несёт одну
  причину. Разбор от этого не зависит: отправитель сверяет подтверждение по
  `type` и `seq` из заголовка.
- `NOTE` с чужим `seq` печатается и попытку не тратит: посторонний ответ —
  часть разговора, а не его отсутствие. `NOTE` с тем же `seq`, что у
  отправленной команды, попытку закрывает, если в этом снимке буфера нет
  `ACK`. Ответ уже пришёл; ждать потерянный `ACK` и слать команду снова —
  значит доставлять её второй раз. Чужой `ACK` попытку не сжигает.

Эхо. По умолчанию на каждый `CMD` кроме `ACK` уходит `NOTE` с тем же текстом
байт-в-байт. Это дешёвая проверка кодовой страницы: если стороны разошлись в
кодировке, отправитель увидит `?` вместо кириллицы сразу. Возврат payload без
перекодирования принципиален — перекодированное эхо выглядело бы правильным и
на разных кодировках, и на одинаково неверных.

Исполнение (`--exec` на приёмнике) заменяет эхо запуском команды; вывод
возвращается несколькими `NOTE` (потолок — 4096 байт: кадр держит 240, а одна
`type big.log` иначе забила бы канал на минуты).

Команда длиннее кадра режется до `build_frame`. Кадр по-прежнему не длиннее
240 байт, и `build_frame` на большем payload по-прежнему бросает `ValueError`.
Текст, который влезает в 240 байт cp866, уходит одним `CMD`, payload — сам
текст. Текст длиннее режется на куски по 232 байта. В каждый `CMD` перед
данными кладётся заголовок из 8 байт: `00 53 45 47 31`, затем `group`,
`index`, `count`. Это байты `\x00SEG1`. Нулевой байт обычная команда не
начинает, поэтому короткий текст с таким заголовком не путается: заголовок
ставится только когда команда в один кадр не влезает. `group` — `seq` первого
куска, `index` с нуля, `count` от 2 до 255.

Все куски одной команды пишутся в буфер одной записью. Отдельная запись на
каждый кусок на живом редиректе теряет второй: первый успевает подтвердиться,
следующий в слот собеседника уже не попадает. Приёмник складывает куски и
только на последнем запускает команду или шлёт эхо целиком. Отправитель ждёт подтверждение последнего куска. Если следующие куски уже
лежат в слоте, приёмник не пишет промежуточный ACK отдельной записью: наружу
уходит один ответ на последний кусок. Отдельный ACK успевал доехать, а ответ
за ним — нет. На промежуточный кусок уходит один `ACK`, без `NOTE` и без
запуска. Повтор куска с тем же `seq` отдаёт закешированный ответ и команду
второй раз не запускает. Команда, которая сама начинается с нулевого байта
и `SEG1`, будет принята за кусок; обычный текст cmd так не начинается.

## 5. Ошибки: NAK, молчание, потеря кадра

Причина отказа передаётся одним байтом в payload `NAK`:

| Код  | Причина       | Когда                          |
|------|---------------|--------------------------------|
| 0x01 | `NAK_CRC`     | контрольная сумма не сошлась   |
| 0x02 | `NAK_TYPE`    | тип кадра не известен приёмнику |
| 0x03 | `NAK_LENGTH`  | длина не бьётся с заголовком   |

Правила, из которых вырос протокол:

- **Кадр с нечитаемым заголовком отбрасывается молча.** `seq` из заголовка —
  единственный способ адресовать ответ; без него подтверждение было бы
  бессмысленным.
- **Неизвестный тип обязан дать NAK, а не игнорироваться.** Иначе сторона новой
  версии молча не дождётся ответа, и это будет неотличимо от обрыва.
- **Молчание приёмника неотличимо от его спокойствия**, поэтому живой собеседник
  отмечается по любому принятому от него кадру, а не только по `PONG`. Порог —
  `--ping` × 3; по умолчанию 25 × 3 = 75 с. Порог ниже `MIN_SILENCE_S = 30`
  помечается предупреждением: RDP-редирект буфера запаздывает сам на
  10–15 с, и на коротком интервале живой канал начал бы выглядеть потерянным.
- **Приёмник не заводит своих `PING`.** Ответная сторона шлёт только `PONG`:
  двусторонний пинг удваивает число записей в слот, а каждая запись — ещё и
  событие RDP-редиректа; на лагающем редиректе heartbeat превращается в шум,
  который сам мешает обмену.
- **Принятый кадр не должен теряться на служебной логике.** Первая потеря CMD на
  живом буфере случилась именно так: кадр читался, обрабатывался heartbeat-ом и
  не доходил до обработки, потому что после `heartbeat_tick` стоял `continue`.
  Приём и разбор собраны в один шаг (`rx.step`), и регресс-тест проверяет, что
  `PING` не съедает уже принятый кадр.
- **Запись в слот перечитывается прямо перед записью.** Атомарного
  «прочитать и изменить» буфер не даёт, поэтому номер буфера сверяется непосредственно
  перед `SetClipboardData`; при расхождении текст слота собирается заново, до
  `PUBLISH_TRIES = 3` раз. Окно между «увидели чужую ячейку» и «записали свою»
  должно быть минимальным: в него терялась первая попытка CMD.
- **Номер буфера приходит раньше текста.** Пока номер слота молчит, буфер
  не открываем: частый опрос не даёт ответу сесть. После нового номера
  строка читается сразу. Если она ещё прежняя, номер не закрывается:
  сверка раз в секунду идёт всё время ожидания.
- **Снимок крупнее 16 КБ в одну запись не кладётся.** Этот размер редирект
  увозит: первая запись часто остаётся на хосте, повтор тех же байт новой
  ячейкой через секунду доходит. 64 КБ — четыре такие записи. Следующая
  начинается после ответа на текущую. История своих ячеек в следующий
  снимок не переносится, иначе слот снова вырастает за предел.
- **Первая запись после чужого снимка часто не уезжает.** Если за секунду
  ответа нет, те же байты публикуются ещё раз новой ячейкой, и на этом
  запись останавливается. Собеседник такую пару ещё не принимал, поэтому
  кадр для него новый, а повтор команды с тем же `seq` берётся из кэша.
  Серия записей чаще одного раза буфер не отпускает и стирает ответ.
  Быстрый ответ так не повторяем: повтор стёр бы следующую команду.
  Ответ после команды, которая исполнялась дольше 8 с, публикуется ещё
  раз одной новой ячейкой. Это первая запись за долгое молчание, без неё
  она остаётся на приёмнике, пока отправитель ещё ждёт. Если к моменту повтора в очереди уже лежит чужой
  кадр, повтор не пишется сразу и не отменяется: таймер сдвигается на
  секунду. Немедленная запись стёрла бы кадр, а сброс таймера потерял бы
  единственную вторую запись.

## 6. Кодовая страница

Payload текстовых кадров — `cp866`. Обе половины канала — Windows, где
`cmd.exe` живёт в OEM-странице; кириллица в `cp866` сохраняется.
У аудио-предшественника была `cp437`: там другой конец — Linux-терминал, а
`cp437` кириллицы не содержит вовсе и через `errors="replace"` молча
превращала `уцкуцк` в `??????` ещё до отправки.

Симметричные места, где текст тоже обязан читаться в `cp866`, а не в локальной
ANSI-странице:

- вывод `--exec` читается байтами и декодируется явно: `text=True` в
  `subprocess` декодировал бы его `cp1251`, и кириллица терялась бы до
  попадания в кадр;
- эхо возвращает payload байт-в-байт (см. раздел 4).

Обе стороны обязаны использовать одну страницу; `--codepage` меняет её на обеих
одинаково.

## 7. Heartbeat

`PING` шлёт отправитель каждые `--ping` секунд (0 — выключить). Приёмник
отвечает `PONG` с тем же `seq` и своих пингов не заводит. `PONG` на `PONG` не
отвечает никогда — иначе обмен бесконечен.

Отправка `PING` сдвигает и дедлайн молчания: свой кадр — доказательство, что мы
сами ещё активны, а пауза в обмене не должна превращаться в ложный обрыв.

Повтор своего снимка новой ячейкой по умолчанию ждёт 1.0 с. Сторона, которая
шлёт команды, измеряет наименьшую паузу, на которой этот повтор ещё доходит:
в начале сеанса, после обмена без подтверждения и когда команд не было
дольше `PACE_IDLE_S`. Быстрый первый уход записи (около 0.1 с) пределом не
считается — он не проверяет повтор. В работу берётся измеренный предел,
умноженный на `PACE_MARGIN` (1.33): на стенде предел 0.7 с даёт 0.94 с.
Короче предела повтор начинает стирать ответ. Формат кадра от замера не
меняется. Приёмник на эти `PING` отвечает обычным `PONG` и своих замеров не
заводит, пока сам не простаивает без команд.

|-----------------|----------|---------------------------------------------------|
| `SYNC_BYTE`     | 0x7E     | начало кадра                                      |

| `PACE_IDLE_S`   | 180 с    | простой без команд до повторного замера           |
| `--wait`        | 1 с      | сколько ждать ответа на кадр                      |

## 9. Как проверить без второй машины

`--slot file:PATH` заменяет буфер обмена файлом, и оба конца запускаются
скриптом на одной машине. Хранилище отслоено (`WindowsClipboard` /
`MemoryClipboard` / `FileClipboard`), поэтому маркер, фильтрация своих кадров,
занятость, пауза и restore проверяются без Windows API.

```
python tools/test_frames.py      # кадр, CRC, разбор, точка входа
python tools/test_clipboard.py   # слот: маркер, история, пауза, занятость
python tools/test_heartbeat.py   # PING/PONG, молчание, resync
python tools/test_duplex.py      # tx и rx двумя процессами
```

## 10. Что намеренно не делается

- Шифрование и аутентификация. Канал идёт в буфере, который читает любое
  приложение сессии; метка стороны — от рассинхронизации, а не от чужого
  процесса. Для чувствительных команд канал не предназначен.
- Передача файлов. Поток по 240 байт с подтверждением на каждый кадр — это
  минуты на мегабайт; для файлов есть сам RDP.
- Терминал с окном и клавиатурой. `--exec` сознательно остаётся запуском одной
  команды с возвратом вывода.
- Несколько отправителей в один слот. Ячейки подписаны, но очередь на
  подтверждение одна.
