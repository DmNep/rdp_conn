# Приёмка rdp_conn на двух машинах: справка для тестирующего агента

Документ — handover: по нему агент поднимает виртуальную машину, получает
стенд «две Windows через RDP» и прогоняет канал по сценариям приёмки.
Читать вместе с `docs/protocol.md` (формат обмена) и `AGENTS.md` (чего не
делать). Числа протокола — только в `rdpconn/config.py`.

База приёмки: пакет 1.0.0, коммит `e4bc398`. На машине разработки
(Windows 11, Python 3.12.10) четыре локальных теста зелёные —
`RESULT: ALL GREEN` у каждого (27.10.2026).

## 1. Что принимается

Канал управления между двумя Windows через буфер обмена RDP:
отправитель (`rdpconn.tx`) на машине с mstsc, приёмник (`rdpconn.rx`) внутри
RDP-сессии. Шаг: `CMD` → `ACK` (кадр дошёл) → `NOTE` (эхо или вывод `--exec`).

Принять — значит подтвердить сценарии раздела 6 на живом RDP-редиректе буфера
и передать цифры раздела 7. Локальные тесты раздела 4 — необходимое, но
недостаточное условие: редирект буфера живёт только между машинами,
подменить его локальным слотом нельзя.

## 2. Стенд: две машины через виртуальную машину

```
хост (машина A, tx)  ──mstsc, редирект буфера──  ВМ (машина B, rx внутри сессии)
```

Требования к ВМ:

- Любая Windows 10/11-гостья с включённым RDP; гипервизор любой
  (Hyper-V, VirtualBox, VMware), сеть — internal/NAT/vSwitch, лишь бы
  с хоста достучаться до 3389.
- **Подключаться к ВМ именно `mstsc` с хоста.** Консоль Hyper-V
  (vmconnect) без enhanced session буфер не редиректит; «общий буфер
  обмена» VirtualBox/VMware — не RDP-редирект, для приёмки не годится,
  это другой транспорт.
- Внутри сессии на ВМ процесс `rdpclip.exe` обязан работать (он и двигает
  буфер; если убит — редиректа нет, `tasklist | findstr rdpclip`).
- На хосте в mstsc: Local Resources → Local devices and resources →
  **Clipboard** отмечен. На ВМ не должно быть GPO «Запретить перенаправление
  буфера обмена» (клиентской и серверной половины).
- На хосте отключить историю буфера (Win+V) и облачную синхронизацию
  буфера: они пишут в слот между нашими кадрами и портят прогон.

Права администратора каналу не нужны ни на одной стороне. Ставится на
обычную учётную запись.

Каталоги: на хосте и на ВМ — по копии проекта, например
`C:\projects\rdp_conn` и `D:\rdp_conn`. Перенос без интернета:
`python tools/make_portable.py` → `rdp_conn_portable.zip` (зависимостей
нет, на ВМ нужен только Python 3.10+, внутри архива — INSTALL.txt).

Проверка, что редирект вообще жив, до всяких прогонов: на хосте
`ctrl+c` текста, в Блокнот внутри RDP-сессии — `ctrl+v`. Не появилось —
стенд не собран, дальше идти бессмысленно.

## 3. Запуск канала (боевые команды)

Сторона B (внутри RDP-сессии, окно mstsc):

```bat
cd /d D:\rdp_conn
set PYTHONPATH=%CD%
py -m rdpconn rx --peer-id B --exec --hotkey ctrl+alt+f9
```

Сторона A (хост, отдельная консоль, mstsc запущен):

```bat
cd /d C:\projects\rdp_conn
set PYTHONPATH=%CD%
py -m rdpconn tx --peer-id A --repl --reply-wait 5 --hotkey ctrl+alt+f9
```

Три вещи без которых прогон бессмыслен (AGENTS.md 3):

- **Ровно один `rx` на B.** Два приёмника с одним `--peer-id` дают шторм
  подтверждений: визуально работает, тонет в повторе. Проверка:
  `tasklist /fi "IMAGENAME eq python.exe"` на B.
- **`--peer-id` задан на обеих сторонах и различается.** Без него метка
  случайная, перезапуск = новый конец, старые ячейки — чужое наследие.
- **`--ping` не ниже 10** (или 0 — выключить). Порог молчания = `--ping`×3;
  на живом редиректе короткий интервал объявляет живой канал потерянным.
  На локальной ВМ редирект быстрый, но для сопоставимости с полевым
  стендом держать `--ping 25` (по умолчанию).

`--hotkey` на обеих сторонах — но помни: пока фокус в окне mstsc,
Ctrl+Alt+F9 уходит в сессию, то есть паузе `rx`. Паузить `tx` — переключив
фокус на хост.

## 4. Этап 0: локальные проверки на каждой машине

На хосте и на ВМ отдельно, каждая команда завершается `RESULT: ALL GREEN`:

```bat
cd /d <каталог проекта>
set PYTHONPATH=%CD%
python tools\test_frames.py      :: кадр, CRC 0x29B1, NAK-коды, точка входа
python tools\test_clipboard.py   :: слот: маркер, история, busy, пауза, restore
python tools\test_heartbeat.py   :: PING/PONG, молчание, resync после обрыва
python tools\test_duplex.py      :: tx и rx двумя процессами через file:PATH
```

Секция «совместимость кадров с xconn_channel» пропустится — так и должно
быть, аудио-проекта рядом нет.

Короткий сквозной прогон одной машиной (проверяет CLI и file-слот на ВМ,
где ещё нет канала):

```bat
:: консоль 1
py -m rdpconn rx --slot file:%TEMP%\slot.txt --peer-id B --ping 0 --duration 30 --exec
:: консоль 2
py -m rdpconn tx --slot file:%TEMP%\slot.txt --peer-id A --ping 0 --reply-wait 2 "echo hello"
```

Ожидаем на tx: `<< ACK seq=0`, `<< NOTE ... 'hello'`; на rx: `<< CMD`,
`>> ACK seq=0`, `>> NOTE seq=0`.

## 5. Этап 1: живой обмен

После запуска раздела 3 на tx (`tx>`):

```
tx> hostname
```

Ожидаем полный шаг: `>> CMD seq=N` → `<< ACK seq=N` → `<< NOTE seq=N
<вывод hostname>`. На rx зеркально: `<< CMD`, `>> ACK`, `>> NOTE`.
На локальной ВМ шаг займёт доли секунды — это нормально и оптимистично
(полевой редирект даёт 10–15 с, docs/protocol.md 5).

## 6. Сценарии приёмки

Каждый сценарий — команда на tx, ожидаемый признак. Итог в отчёт: PASS /
FAIL + строки вывода.

| # | Сценарий | Действие | Ожидаем |
|---|---|---|---|
| S1 | Базовый шаг | `tx> hostname` | CMD→ACK→NOTE, вывод `hostname` дошёл |
| S2 | `--exec` большой вывод | `tx> cmd /c set` | вывод возвращается несколькими NOTE (потолок 4096 Б), tx печатает их все |
| S3 | Кириллица (cp866) | `tx> echo привет` | в NOTE читается «привет», не `??????` |
| S4 | Кода страницы | `tx> chcp` на B | ответ содержит 866; при другой — зафиксировать, лечится одинаковым `--codepage` на обеих |
| S5 | Рестарт приёмника | убить `rx` (Ctrl+C), запустить заново, отправить команду | команда дошла с первого раза: приём по паре (номер, содержимое), счётчик с единицы его не глушит |
| S6 | Обрыв и возврат | убить `rx`, ждать на tx; затем поднять `rx` | tx через ~`--ping`×3 с печатает «собеседник молчит … — канал считается потерянным»; после поднятия — «.. собеседник снова отвечает», обмен продолжается |
| S7 | Пауза клавишей | Ctrl+Alt+F9 (фокус там, где нужный конец) | «!! обмен на паузе…»; copy/paste человеком работает; повторное нажатие — «<< обмен продолжен»; с `--restore` последний наш кадр вернулся в слот |
| S8 | Человеческая копия (busy) | в сессии Блокнотом скопировать любой текст | rx говорит «.. в слоте чужая копия…», обмен НЕ встал: следующая команда проходит; занятость снялась сама через `--pause-timeout` (60 с) |
| S9 | Таймаут команды | `tx> cmd /c ping -n 40 127.0.0.1` | через `--exec-timeout` (20 с) в NOTE: «команда прервана по таймауту 20 с» |
| S10 | Тишина без приёмника | `rx` не запущен: `py -m rdpconn tx --peer-id A --wait 1 --retries 2 "nikogo"` | tx завершается кодом 1, печатает «тишина», не виснет |
| S11 | Heartbeat между процессами | оба конца с `--ping 25`, молчать | на tx периодические `>> PING` и `<< PONG`; rx своих PING не шлёт (проверить по его логу) |
| S12 | Шторм двух приёмников (диагностика) | запустить на B второй `rx --peer-id B` | удвоенные `<< ACK` на tx — воспроизвели признак, убили второй `rx`, обмен вернулся к норме |
| S13 | Ретрансляция | во время S7 (пауза на B) отправить команду | tx печатает «(попытка 2)», после снятия паузы команда доходит ровно один раз (на B — один `>> ACK`, эхо один) |

Известные границы (фиксировать, не чинить на месте):

- Команда длиннее 240 байт в cp866 уходит несколькими `CMD` и собирается на
  приёмнике до запуска. Кадр по-прежнему не длиннее 240: `build_frame` на
  большем payload бросает `ValueError`.
- `NOTE` с выводом — только текст в кодовой странице tx.

## 7. Замеры для решения о батчинге

### 7.1 Живой RTT (`--remote`)

Единственный режим, видящий редирект. На B остановить штатный `rx` и:

```bat
B: py -m rdpconn.rx --peer-id B --ping 0 --no-echo --wait 25 --duration 900
A: python tools\bench_speed.py --remote --proc-frames 20 --remote-wait 25
```

В отчёт: медиана шага CMD→ACK, Б/с, «время на команду», и обязательно
строка про чистоту прогона. `!! прогон нечист` — цифру не брать, устранить
(чистый слот, один `rx`) и повторить. Предупреждение про `--remote-wait`
меньше 20 с — расчёт на полевой редирект; на локальной ВМ можно и 5 с,
но в отчёте помечать раздельно.

### 7.2 Латентность против пропускной способности (`--bulk`)

```bat
B: python tools\bench_speed.py --bulk-listen --bulk-wait 600   # штатный rx остановить!
A: python tools\bench_speed.py --bulk --bulk-wait 60
```

Ответ в отчёт одной из двух строк вывода скрипта: «задержка почти не
зависит от размера — это латентность, спасает батчинг» против «растёт —
это пропускная способность». Это вход в решение владельца о изменении
протокола, сам протокол не менять.

### 7.3 Ориентиры

Цель под агента — 4000 Б/с (`BULK_TARGET_BPS`). На локальной ВМ редирект
быстрый, цифры будут оптимистичнее поля; задача приёмки — работоспособность
и воспроизводимая методика, а не рекорд.

## 8. Типовые неисправности стенда

| Признак | Причина / проверка |
|---|---|
| `<< ACK` вообще нет, «тишина» | редирект буфера выключен (mstsc Clipboard, GPO), `rdpclip.exe` мёртв в сессии; проверка: сразу после отправки Ctrl+V в Блокнот на B — должен быть текст `RDP1\|A:...` |
| Шторм `<< ACK`, дубли NOTE | второй `rx` на B — см. S12 |
| «ожидался ACK seq=0, получен ACK seq=30», ретрансляции | слот забит наследием прежнего обмена; `--remote` чистит сам, вручную — пауза по `--hotkey` или перезапуск обоих концов |
| `??????` вместо кириллицы | разъехались кодовые страницы; `--codepage` одинаково на обеих |
| «!! в слоте чужая копия» на пустом стенде | история буфера Windows / облачная синхронизация пишут в слот — отключить |
| `rx` молчит, `tx` печатет PING без PONG | `rx` не запущен / упал; проверить консоль B |
| Оба конца стартуют с ошибкой про буфер | запуск из-под сервиса/сессии без окна — буфер доступен только в интерактивной сессии |

## 9. Формат отчёта

1. Стенд: гипервизор, версии Windows хоста и ВМ, Python на обеих, версия mstsc.
2. Этап 0: четыре строки `RESULT` с каждой машины.
3. S1–S13: таблица PASS/FAIL + по FAIL — последние 5 строк вывода обеих сторон.
4. Замеры: `--remote` (медиана, Б/с, чист/нечист) и вывод `--bulk` целиком.
5. Наблюдения вне сценариев (в т.ч. граница 240 байт из раздела 6).

## 10. Чего тестирующему агенту не делать

- Не менять протокол, константы `rdpconn/config.py`, префикс `RDP1` и
  `docs/protocol.md` — расхождения находить и описывать в отчёте, решает
  владелец.
- Не добавлять зависимости и venv — нулевые зависимости это требование.
- Не делать `git init`/push/теги и не трогать соседний аудио-проект
  `../x_conn2`.
- Не оставлять на B второй `rx` и не запускать прогоны с включённой
  историей буфера — это портит чужие замеры.
- Тесты дописывать в стиле существующих: скрипт с `check(...)` и итогом
  `RESULT: ALL GREEN`, без pytest.
