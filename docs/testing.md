# Приёмка rdp_conn на двух машинах: справка для тестирующего агента

Документ — handover: по нему агент поднимает виртуальную машину, получает
стенд «две Windows через RDP» и прогоняет канал по сценариям приёмки.
Читать вместе с `docs/protocol.md` (формат обмена) и `AGENTS.md` (чего не
делать). Числа протокола — только в `rdpconn/config.py`.

База приёмки: пакет 1.0.0, коммит `e4bc398`. На машине разработки
(Windows 11, Python 3.12.10) четыре локальных теста зелёные —
`RESULT: ALL GREEN` у каждого (27.10.2026).

покрывают `gate`/`coder`/`host`/`guest`/`fileshake` (`--drop`), которых не

файла канал откатился на обычные ячейки, и весь ответ (100000 байт)

(`файл не пришёл за 180 с`), не путь исчерпанных ретраев — похоже,
настоящая причина глубже: подозревается гонка между
`GetClipboardSequenceNumber()` и `IsClipboardFormatAvailable()` внутри
`fileclip.wait_for_new_file()` (может один раз молча списать смену seq
без файла и больше не перепроверить — гипотеза, не подтверждена
трассировкой). **G7 подтверждён повторно, чистым прогоном** (без
вмешательства в буфер во время теста) — снова 100000 байт byte-perfect.

**`wait_for_new_file()` починен, тот же день, по решению владельца —

снова не прошёл, с тем же таймаутом** (`файл не пришёл за 180 с`) —
значит, дело не в логике "одной упущенной проверки": на этом стенде
`IsClipboardFormatAvailable(FileGroupDescriptorW)` устойчиво не
возвращает true все 180 секунд, не кратковременная гонка. **G7
подтверждён в третий раз подряд** — снова byte-perfect.

**Win32-трассировка, тот же день — найден настоящий структурный
факт.** Трассировка добавлена внутрь `wait_for_new_file()` и в точку
входа `_receive_bulk()`, прогнана живьём с `RDPCONN_TRACE` на обеих
сторонах одновременно. **Результат:** `dial` честно записал файл за
77 мс, но `GetClipboardSequenceNumber()` на стороне `listen` **не
изменился ни разу за 165+ секунд** (ни одной трассы
`fileclip-wait-seq-change`/`heartbeat`) — редирект не донёс сигнал о
смене буфера вовсе, не кратковременная гонка. При этом десятки ручных
`fileclip send`/`watch`-деплоев в этой же сессии на том же RDP-
соединении всегда срабатывали быстро и надёжно. Рабочая,
непроверенная гипотеза: мешает интенсивный текстовый трафик того же
слота непосредственно перед файловым анонсом (которого не было перед
ручными деплоями). Причина — не в коде `gate.py`/`fileclip.py` (три
фикса этого дня все верны и не виноваты), а глубже — либо в самом
RDP-редиректоре, либо в этом конкретном паттерне использования.
**Изолированный эксперимент, тот же день — гипотеза ОПРОВЕРГНУТА,
причина не в состоянии буфера.** Два чистых теста без `gate.py`
(`tools/exp_burst_then_file.py`/`exp_burst_then_watch.py`) — пачка из
20 быстрых текстовых записей (и односторонняя, и двусторонняя) сразу
перед переключением на файл — **оба раза файл дошёл за 21-22 мс, без

listen` сразу после, на том же соединении, — снова тот же провал
(`файл не подтверждён за 180 с`), уже четвёртый раз подряд. Значит,
дело не в недавнем трафике буфера как таковом — причина специфична
тому, КАК `gate.py` использует `fileclip` изнутри своего процесса
(сложный путь публикации через `ClipboardTransport`'s `_publish_many`
в отличие от простого `WindowsClipboard.write()`, или состояние
долгоживущего процесса) — дальше нужно сравнение кода, не новые живые
пробы. G7 подтверждён в четвёртый раз подряд. Подробности — память
`gate_bulk_oleSetClipboard_hang.md`.

**Сравнение кода, тот же день — G6 ПОЧИНЕН, подтверждён живьём.**
Настоящая причина: `send_snapshot()` безусловно взводит nudge
(отложенный повтор публикации через классический `SetClipboardData`)
для любого кадра, включая анонс `OP_BULK_OFFER`, а `NUDGE_AFTER_S`
(0.94 с) совпадал с собственной settle-паузой `_offer_bulk()` перед
записью файла один-в-один — nudge стирал только что установленный
OLE-файловый объект через ~53 мс после записи, на каждой попытке.
Фикс — `ClipboardTransport.cancel_nudge()`, вызываемый в `_offer_bulk()`
сразу после публикации анонса и симметрично на стороне `listen` при
приёме `OP_BULK_OFFER`, плюс замена одного слепого `sleep(settle)` на
переиздание анонса каждые 0.2 с на протяжении settle-окна (слепой sleep
пропускал анонс целиком, если `listen` в этот момент был занят своей же
публикацией). Подтверждено: локально 22/22 `ALL GREEN`, затем два
отдельных живых прогона — оба с `файл подтверждён` в логе, `curl
HTTP:200 size:100000`, `Get-FileHash` байт-в-байт в обоих случаях;
второй прогон — на свежем, только что переподключённом RDP-соединении.
**G6 и G7 оба закрыты.** Подробности — память
`gate_bulk_oleSetClipboard_hang.md`.

## 1. Что принимается

Канал управления между двумя Windows через буфер обмена RDP:
отправитель (`rdpconn.tx`) на машине с mstsc, приёмник (`rdpconn.rx`) внутри
RDP-сессии. Шаг: `CMD` → `ACK` (кадр дошёл) → `NOTE` (эхо или вывод `--exec`).

Принять — значит подтвердить сценарии раздела 6 на живом RDP-редиректе буфера
и передать цифры раздела 7. Локальные тесты раздела 4 — необходимое, но
недостаточное условие: редирект буфера живёт только между машинами,
подменить его локальным слотом нельзя.

Поверх того же слота и формата кадра `NOTE` выросли дополнительные конечные
точки (AGENTS.md §1): `gate` (HTTP-прокси, магия `G1`), `coder`/`host`/`guest`
(текст локальной модели для Cline, магия `C1`, служебная ячейка статистики
`S1`) и `fileshake`/`--drop` (реальные файлы через `FileGroupDescriptorW`/
`FileContents`, рукопожатие `F1`). Разделы 6.1–6.3 — их сценарии приёмки.

## 2. Стенд: две машины через виртуальную машину

```
хост (машина A, tx)  ──mstsc, редирект буфера──  ВМ (машина B, rx внутри сессии)
```

Требования к ВМ:

- Любая Windows 10/11-гостья с включённым RDP; гипервизор любой
  (Hyper-V, VirtualBox, VMware), сеть — internal/NAT/vSwitch, лишь бы
  с хоста достучаться до 3389.
- **Подключаться к ВМ именно `mstsc` с хоста.** Консоль Hyper-V
  (vmconnect) без enhanced session буфер не редиректит; «общий буфер
  обмена» VirtualBox/VMware — не RDP-редирект, для приёмки не годится,
  это другой транспорт.
- Внутри сессии на ВМ процесс `rdpclip.exe` обязан работать (он и двигает
  буфер; если убит — редиректа нет, `tasklist | findstr rdpclip`).
- На хосте в mstsc: Local Resources → Local devices and resources →
  **Clipboard** отмечен. На ВМ не должно быть GPO «Запретить перенаправление
  буфера обмена» (клиентской и серверной половины).
- На хосте отключить историю буфера (Win+V) и облачную синхронизацию
  буфера: они пишут в слот между нашими кадрами и портят прогон.

Права администратора каналу не нужны ни на одной стороне. Ставится на
обычную учётную запись.

Каталоги: на хосте и на ВМ — по копии проекта, например
`C:\projects\rdp_conn` и `D:\rdp_conn`. Перенос без интернета:
`python tools/make_portable.py` → `rdp_conn_portable.zip` (зависимостей
нет, на ВМ нужен только Python 3.10+, внутри архива — INSTALL.txt).

Проверка, что редирект вообще жив, до всяких прогонов: на хосте
`ctrl+c` текста, в Блокнот внутри RDP-сессии — `ctrl+v`. Не появилось —
стенд не собран, дальше идти бессмысленно.

## 3. Запуск канала (боевые команды)

Сторона B (внутри RDP-сессии, окно mstsc):

```bat
cd /d D:\rdp_conn
set PYTHONPATH=%CD%
py -m rdpconn rx --peer-id B --exec --hotkey ctrl+alt+f9
```

Сторона A (хост, отдельная консоль, mstsc запущен):

```bat

py -m rdpconn tx --peer-id A --repl --reply-wait 5 --hotkey ctrl+alt+f9
```

Три вещи без которых прогон бессмыслен (AGENTS.md 3):

- **Ровно один `rx` на B.** Два приёмника с одним `--peer-id` дают шторм
  подтверждений: визуально работает, тонет в повторе. Проверка:
  `tasklist /fi "IMAGENAME eq python.exe"` на B.
- **`--peer-id` задан на обеих сторонах и различается.** Без него метка
  случайная, перезапуск = новый конец, старые ячейки — чужое наследие.
- **`--ping` не ниже 10** (или 0 — выключить). Порог молчания = `--ping`×3;
  на живом редиректе короткий интервал объявляет живой канал потерянным.
  На локальной ВМ редирект быстрый, но для сопоставимости с полевым
  стендом держать `--ping 25` (по умолчанию).

`--hotkey` на обеих сторонах — но помни: пока фокус в окне mstsc,
Ctrl+Alt+F9 уходит в сессию, то есть паузе `rx`. Паузить `tx` — переключив
фокус на хост.

## 6. Сценарии приёмки

Каждый сценарий — команда на tx, ожидаемый признак. Итог в отчёт: PASS /
FAIL + строки вывода.

| # | Сценарий | Действие | Ожидаем |
|---|---|---|---|
| S1 | Базовый шаг | `tx> hostname` | CMD→ACK→NOTE, вывод `hostname` дошёл |
| S2 | `--exec` большой вывод | `tx> cmd /c set` | вывод возвращается несколькими NOTE (потолок 4096 Б), tx печатает их все |
| S3 | Кириллица (cp866) | `tx> echo привет` | в NOTE читается «привет», не `??????` |
| S4 | Кода страницы | `tx> chcp` на B | ответ содержит 866; при другой — зафиксировать, лечится одинаковым `--codepage` на обеих |
| S5 | Рестарт приёмника | убить `rx` (Ctrl+C), запустить заново, отправить команду | команда дошла с первого раза: приём по паре (номер, содержимое), счётчик с единицы его не глушит |
| S6 | Обрыв и возврат | убить `rx`, ждать на tx; затем поднять `rx` | tx через ~`--ping`×3 с печатает «собеседник молчит … — канал считается потерянным»; после поднятия — «.. собеседник снова отвечает», обмен продолжается |
| S7 | Пауза клавишей | Ctrl+Alt+F9 (фокус там, где нужный конец) | «!! обмен на паузе…»; повторное нажатие — «<< обмен продолжен». Без чужого текста `--restore` кладёт последний кадр новой ячейкой. Если за паузу человек скопировал своё, этот текст остаётся и после снятия паузы |
| S8 | Человеческая копия (busy) | в сессии Блокнотом скопировать любой текст | rx говорит «.. в слоте чужая копия…», обмен НЕ встал: следующая команда проходит; занятость снялась сама через `--pause-timeout` (60 с) |
| S9 | Таймаут команды | `tx> cmd /c ping -n 40 127.0.0.1` | через `--exec-timeout` (20 с) в NOTE: «команда прервана по таймауту 20 с» |
| S10 | Тишина без приёмника | `rx` не запущен: `py -m rdpconn tx --peer-id A --ping 1 "nikogo"` | tx шлёт `PING` трижды, затем завершается кодом 1 с «собеседник молчит … потерянным», укладывается в ~3 с (`--ping`×3), не виснет. `--wait`/`--retries` на эту тишину уже не влияют — см. протокол 5; с `--ping 0` поведение старое: короткий `--wait`×`--retries` и «тишина N с» |
| S11 | Heartbeat между процессами | оба конца с `--ping 25`, молчать | на tx периодические `>> PING` и `<< PONG`; rx своих PING не шлёт (проверить по его логу) |
| S12 | Шторм двух приёмников (диагностика) | запустить на B второй `rx --peer-id B` | удвоенные `<< ACK` на tx — воспроизвели признак, убили второй `rx`, обмен вернулся к норме |
| S13 | Ретрансляция | во время паузы на B отправить команду | tx печатает «(попытка 2)», после снятия паузы хост получает один NOTE. Команда на B не запускается второй раз; повторный приём той же команды всё равно получает свой ACK |

Известные границы (фиксировать, не чинить на месте):

- Команда длиннее 240 байт в cp866 уходит несколькими `CMD` и собирается на
  приёмнике до запуска. Кадр по-прежнему не длиннее 240: `build_frame` на
  большем payload бросает `ValueError`.
- `NOTE` с выводом — только текст в кодовой странице tx.

## 6.1 Сценарии приёмки: gate (HTTP-прокси через буфер)

`gate listen` — машина без сети (внутри сессии), поднимает локальный прокси.
`gate dial` — машина с сетью (хост), выпускает байты в обычный TCP. Раскладка
кадра та же, своя магия `G1` живёт внутри `NOTE` (AGENTS.md §1).

Запуск:

```bat
B (listen, внутри сессии): python -m rdpconn gate listen --peer-id B --proxy 127.0.0.1:8079
A (dial, хост):            python -m rdpconn gate dial --peer-id A
```

На B — любой HTTP-клиент с прокси `127.0.0.1:8079` (`curl -x 127.0.0.1:8079 ...`
или настройки прокси в браузере сессии).

| # | Сценарий | Действие | Ожидаем |
|---|---|---|---|
| G1 | Базовый запрос | через прокси на B запросить ресурс, доступный с A | ответ дошёл целиком, тело совпало байт-в-байт |
| G2 | Простой без запросов | не слать запросов 2+ минуты, затем новый запрос | канал не завис и не заштормил слот во время простоя (бэкофф тишины `listen_loop`, docs/protocol.md 10); первый запрос после простоя может быть заметно медленнее следующих — это не брак |
| G3 | Человеческая копия во время передачи | Ctrl+C текста в сессии B пока через прокси идёт крупный ответ | передача не портится и не теряет данные, слот освобождается сам (аналог S8, но для gate) |
| G4 | Переподключение mstsc | отключить и переподключить RDP-сессию на B, пока `gate` жив | **на новом подключении вручную отметить чекбокс Clipboard в диалоге «unknown publisher»** — mstsc сбрасывает его при каждом переподключении независимо от .rdp-файла (известная грабля, не код); после этого обмен возобновляется сам |
| G5 | Крупный файл через прокси | скачать через прокси файл в несколько МБ | передача завершается, не висит на потолке ячеек (`GATE_CELLS_MAX`); зафиксировать время и посчитанную скорость в отчёте — отдельного норматива для gate нет, цифра информативная |
| G6 | Крупный кусок уходит файлом (`docs/roadmap.md` 5) | скачать через прокси ответ больше `BULK_THRESHOLD` (48 КБ по умолчанию с 28.11.2026, было 128 КБ — см. `gate_bulk_window_threshold_bug.md`) | в логе `.. поток N: … байт файлом вместо ячеек` и `… файл подтверждён`; тело совпало байт-в-байт; **28.11.2026: три живых фикса (offset-якорь, retry-бюджет, `wait_for_new_file()`) и изолированный эксперимент, ни один не закрыл G6 — причина не в коде фиксов и не в недавнем текстовом трафике буфера (оба исключены живьём), а в том, КАК именно `gate.py` использует `fileclip` изнутри своего процесса**, `… файл подтверждён` живьём так и не увидели, см. `gate_bulk_oleSetClipboard_hang.md`** |
| G7 | Откат с файла на ячейки живьём | во время G6 имитировать сбой (например, разорвать RDP на пару секунд сразу после анонса) или просто повторить G6 несколько раз подряд и смотреть на редкие сбои COM (`CLIPBRD_E_CANT_OPEN`/`DV_E_FORMATETC`, см. докстринг `fileclip.py`) | тело всё равно доходит целиком (через обычные ячейки), в логе `... прошу откат на ячейки`; поток не виснет и не теряет данные; **28.11.2026 ПОДТВЕРЖДЕНО ЖИВЬЁМ, четыре раза подряд (включая чистые прогоны без вмешательства в буфер)**: все 100000 байт все четыре раза дошли byte-perfect (`sha256` совпал) — откат работает надёжно и не теряет данные, см. `gate_bulk_oleSetClipboard_hang.md` |

Известная особенность (не баг, фиксировать при замерах): пропускная
способность `gate` асимметрична по направлению (A→B и B→A отличались на
лабораторном стенде почти вдвое, см. память проекта) — не делать вывод о
регрессии по одному направлению без сравнения со вторым.

## 6.2 Сценарии приёмки: coder / host / guest (локальная модель)

`coder host` — рядом с моделью (OpenAI-совместимый сервер, например
`llama-server`, на этой же машине). `coder guest` — внутри сессии, тот текст,
который в бою видит провайдер Cline (`cline/rdpconnHandler.ts`). Магия `C1`

этим можно проверять приёмку без настройки самого Cline.

Запуск:

```bat
A (host, рядом с моделью): python -m rdpconn coder host --peer-id A --upstream http://127.0.0.1:8080/v1
B (guest, в сессии):       python -m rdpconn coder guest --peer-id B --once once.json
```

`once.json` — объект с полями, которые шлёт Cline (`system`, `messages`);
формат точно смотреть в `cline/rdpconnHandler.ts`, не придумывать свой.

| # | Сценарий | Действие | Ожидаем |
|---|---|---|---|
| C1 | Базовый запрос-ответ | один `--once` с коротким промптом | guest напечатал `{"done":true}` в stdout после того, как текст ответа пришёл частями |
| C2 | Второй guest в той же сессии | запустить второй `coder guest` пока первый работает | второй сразу печатает «кодер уже в сессии» и выходит кодом 0 (`claim_guest()`), первому не мешает |

| C4 | Длинный ответ | промпт, провоцирующий ответ крупнее одного снимка (`--cells`) | ответ собрался полностью, без потери хвоста (тот же класс риска, что S2, но для C1 и другого размера ячейки) |
| C5 | Страница статистики (`--feed model`) | `python -m rdpconn host --feed model` вместо `coder host`, открыть `http://127.0.0.1:8078` в браузере на A во время генерации | страница отражает текущее состояние (служебная ячейка `S1`, `rdpconn/statcell.py`) и обновляется |
| C6 | Кириллица в промпте и ответе | промпт и ожидаемый ответ с кириллицей | дошла без `??????` (тот же риск, что S3, но в C1-кадре, не в текстовом echo) |

(`ok`, затем кириллический промпт/ответ про кота Барсика) прошли чисто —
`host-unpacked-request` → `model-to-host` → `host-sent-reply` → у guest
`{"text": ...}` → `{"done":true}`, без единого `??????`. Перед прогоном в

прогоном: персистентный guest с двумя запросами подряд через stdin получил

## 6.3 Сценарии приёмки: fileshake / `--drop` (файлы)

Самая новая часть (доведена 27.11.2026, три живых бага починены в процессе —
см. память проекта `fileclip_text_channel_handshake_design.md`). Работает
поверх того же слота и кадра `NOTE`, но несёт настоящий файл через
`FileGroupDescriptorW`/`FileContents` (на порядки быстрее текста), не
base64 в payload. Магия `F1`. Запускается через `host`/`guest --feed model
--drop <папка>` (`ends.py`, только с `--feed model`): `DropWatcher` следит за
`<папка>\out\*`, доставляет их собеседнику, а входящие кладёт в
`<папка>\in\`, отправленные уходят в `<папка>\out\sent\`.

Запуск:

```bat
A: python -m rdpconn host --feed model --drop C:\drop_a --upstream http://127.0.0.1:8080/v1
B: python -m rdpconn guest --feed model --drop D:\drop_b
```

| # | Сценарий | Действие | Ожидаем |
|---|---|---|---|
| F1 | Передача A→B | положить файл в `C:\drop_a\out\` | файл появился в `D:\drop_b\in\`, sha256 совпал; исходный файл ушёл в `C:\drop_a\out\sent\` |
| F2 | Передача B→A | положить файл в `D:\drop_b\out\` | файл появился в `C:\drop_a\in\`, sha256 совпал |
| F3 | Несколько файлов разом | положить 2–3 файла в `out\` одной пачкой (один тик `DropWatcher`) | все дошли, имена и размеры совпали (`FileGroupDescriptorW.cItems > 1`, не только одиночный случай) |
| F4 | Отказ виден отправителю | остановить процесс на принимающей стороне перед тем, как класть файл (offer уходит в таймаут) | на отправляющей стороне понятная ошибка, не тихое зависание; файл остаётся в `out\`, не помечен как отправленный |
| F5 | Файл одновременно с активным запросом к модели | положить файл в `out\`, пока идёт запрос через `coder`/C1 | оба доходят по отдельности и без порчи (`file_lock` в `_guest_with_drop`, `rdpconn/ends.py`), ни один не теряется |
| F6 | Устойчивость COM-инициализации | подряд 5+ передач файлов через `--drop` без перезапуска процессов | ни одна не упала с `CLIPBRD_E_BAD_DATA`/`0x80040064`; баг был нерегулярным (не на первой попытке), поэтому один успешный прогон НЕ считается подтверждением — нужно несколько подряд |
| F7 | Переподключение mstsc во время ожидания | отключить/подключить RDP, пока файл лежит в `out\` и ждёт отправки (не забыть чекбокс Clipboard — см. G4) | файл не теряется, уходит после восстановления редиректа |

## 7. Замеры для решения о батчинге

### 7.1 Живой RTT (`--remote`)

Единственный режим, видящий редирект. На B остановить штатный `rx` и:

```bat
B: py -m rdpconn.rx --peer-id B --ping 0 --no-echo --wait 25 --duration 900
A: python tools\bench_speed.py --remote --proc-frames 20 --remote-wait 25
```

В отчёт: медиана шага CMD→ACK, Б/с, «время на команду», и обязательно
строка про чистоту прогона. `!! прогон нечист` — цифру не брать, устранить
(чистый слот, один `rx`) и повторить. Предупреждение про `--remote-wait`
меньше 20 с — расчёт на полевой редирект; на локальной ВМ можно и 5 с,
но в отчёте помечать раздельно.

### 7.2 Латентность против пропускной способности (`--bulk`)

```bat
B: python tools\bench_speed.py --bulk-listen --bulk-wait 600   # штатный rx остановить!
A: python tools\bench_speed.py --bulk --bulk-wait 60
```

Ответ в отчёт одной из двух строк вывода скрипта: «задержка почти не
зависит от размера — это латентность, спасает батчинг» против «растёт —
это пропускная способность». Это вход в решение владельца о изменении
протокола, сам протокол не менять.

### 7.3 Ориентиры

Цель под агента — 4000 Б/с (`BULK_TARGET_BPS`). На локальной ВМ редирект
быстрый, цифры будут оптимистичнее поля; задача приёмки — работоспособность
и воспроизводимая методика, а не рекорд.

Пауза повтора снимка подстраивается сама (`rdpconn.tune`): в начале сеанса
`tx`, после обмена без подтверждения и на простое без команд дольше 3 минут.
Ищется наименьший повтор, который ещё доходит; в работу берётся он × 1.33.
На стенде это было 0.7 с и 0.94 с. Быстрый первый уход записи (около 0.1 с)
пределом не считается. `--ping 0` замер не отключает: проверка шлёт свой PING.

## 8. Типовые неисправности стенда

| Признак | Причина / проверка |
|---|---|
| `<< ACK` вообще нет, «тишина» | редирект буфера выключен (mstsc Clipboard, GPO), `rdpclip.exe` мёртв в сессии; проверка: сразу после отправки Ctrl+V в Блокнот на B — должен быть текст `RDP1\|A:...` |
| Шторм `<< ACK`, дубли NOTE | второй `rx` на B — см. S12 |
| «ожидался ACK seq=0, получен ACK seq=30», ретрансляции | слот забит наследием прежнего обмена; `--remote` чистит сам, вручную — пауза по `--hotkey` или перезапуск обоих концов |
| `??????` вместо кириллицы | разъехались кодовые страницы; `--codepage` одинаково на обеих |
| «!! в слоте чужая копия» на пустом стенде | история буфера Windows / облачная синхронизация пишут в слот — отключить |
| `rx` молчит, `tx` печатет PING без PONG | `rx` не запущен / упал; проверить консоль B |
| Оба конца стартуют с ошибкой про буфер | запуск из-под сервиса/сессии без окна — буфер доступен только в интерактивной сессии |
| Второй `coder guest`/`guest --feed model` не запускается | ожидаемо: «кодер уже в сессии» — защита от двух гуестов в одной сессии (см. C2), не ошибка |
| `gate`/`coder` работают, но заметно медленнее ожидаемого в одну сторону | асимметрия A↔B у gate — известное наблюдение (раздел 6.1), не само по себе неисправность стенда |
| `--drop` падает `CLIPBRD_E_BAD_DATA`/`0x80040064` нерегулярно | живой баг, чинился в проекте через per-thread `OleInitialize` (см. F6, память проекта); если воспроизвёлся на текущем коде — не локальная гонка стенда, фиксировать и разбирать как регресс |

## 9. Формат отчёта

1. Стенд: гипервизор, версии Windows хоста и ВМ, Python на обеих, версия mstsc.
2. Этап 0: двадцать строк `RESULT` с каждой машины (раздел 4).
3. S1–S13: таблица PASS/FAIL + по FAIL — последние 5 строк вывода обеих сторон.
4. G1–G7, C1–C6, F1–F7 (разделы 6.1–6.3): та же таблица PASS/FAIL; для F6
   отдельно — число подряд успешных прогонов, не только факт первого успеха;
   для G6/G7 — что именно показал лог (файлом/откатом), не только факт PASS.
5. Замеры: `--remote` (медиана, Б/с, чист/нечист) и вывод `--bulk` целиком.
6. Наблюдения вне сценариев (в т.ч. граница 240 байт из раздела 6 и
   направленная асимметрия gate из раздела 6.1).

## 10. Чего тестирующему агенту не делать

- Не менять протокол, константы `rdpconn/config.py`, префикс `RDP1` и
  `docs/protocol.md` — расхождения находить и описывать в отчёте, решает
  владелец.
- Не добавлять зависимости и venv — нулевые зависимости это требование.
- Не делать `git init`/push/теги и не трогать соседний аудио-проект
  `../x_conn2`.
- Не оставлять на B второй `rx` и не запускать прогоны с включённой
  историей буфера — это портит чужие замеры.
- Тесты дописывать в стиле существующих: скрипт с `check(...)` и итогом
  `RESULT: ALL GREEN`, без pytest.
